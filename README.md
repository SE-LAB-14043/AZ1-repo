## شاخه‌ها

برای مدیریت بهتر فرآیند توسعه، پروژه به صورت Branch-Based توسعه داده شده است؛ به این صورت که هر قابلیت جدید در یک شاخه مستقل توسعه داده شده و برای اصلاح مشکلات نیز شاخه‌های جداگانه‌ای در نظر گرفته شده است. پس از تکمیل هر قابلیت، تغییرات ابتدا وارد شاخه `stage` شده و در آنجا مورد بررسی و آزمایش قرار گرفته‌اند. پس از اطمینان از صحت عملکرد، تغییرات از طریق Pull Request به شاخه اصلی پروژه یعنی `main` منتقل شده‌اند.

همچنین شاخه `main` به وسیله قابلیت **Branch Protection** در GitHub محافظت شده است و امکان Push مستقیم به آن وجود ندارد. بنابراین ورود تغییرات به شاخه اصلی تنها از طریق Pull Request انجام می‌شود.

### main

شاخه `main` شاخه اصلی و پایدار پروژه است. نسخه‌ای که در این Branch قرار دارد، نسخه‌ای است که پس از بررسی و تأیید تغییرات آماده انتشار محسوب می‌شود.


### stage


شاخه `stage` به عنوان محیط میانی برای بررسی و آزمایش تغییرات استفاده شده است.

هدف از ایجاد این Branch این بوده است که تغییرات قبل از ورود به `main` یک مرحله کنترل و تست را پشت سر بگذارند.

و تست را پشت سر بگذارند.

روند کلی به این صورت بوده است:

```text
Feature / Fix Branch
        ↓
      stage
        ↓
      Test
        ↓
   Pull Request
        ↓
      main
```

به عنوان مثال، زمانی که توسعه یک قابلیت در Branch مربوط به آن به پایان می‌رسید، تغییرات آن ابتدا وارد stage می‌شدند. در این مرحله عملکرد قابلیت جدید در کنار سایر قسمت‌های پروژه بررسی می‌شد تا مشکلات احتمالی مانند ناسازگاری بین قابلیت‌ها، خطاهای ظاهری  مشخص شوند.

### features

برای هر قابلیت جدید پروژه یک Branch مستقل ایجاد شده است تا توسعه هم بتواند به صورت موازی پیش برود و هم مستقل از شاخه‌های دیگر باشد.

برای مثال Branch‌های زیر در پروژه ایجاد شده‌اند:


```text
feature/home-page
feature/nav-bar
feature/footer
feature/about-page
feature/loan-page
feature/profit-page
```

### fix

برای برطرف کردن Bug‌ها یا مشکلات موجود در پروژه نیز Branch‌های جداگانه ایجاد شده‌اند.
برای مثال اگر بعد از تست در stage مشخص شود که یک قابلیت دارای مشکل است، به جای تغییر مستقیم stage یا main، یک Branch مخصوص رفع مشکل ایجاد می‌شود. مثل


```text
fix/repo-address-fix
```

### docs

برای اضافه کردن اسناد لازم در پروژه. مثلا اینجا اضافه کردن گزارش پروژه و پاسخ به سوالات

```text
docs/complete-readme
```

## پوشه‌ی .git چیست؟ چه اطلاعاتی در آن ذخیره می‌شود؟ با چه دستوری ساخته می‌شود؟

پوشهٔ `.git` شامل همهٔ داده‌ها و ساختارهای درونی است که Git برای مدیریت نسخهٔ یک پروژه نیاز دارد. این دایرکتوری به یک پایگاه دادهٔ محلی تبدیل می‌شود که تاریخچهٔ کامل، شاخه‌ها، تگ‌ها و پیکربندی‌های مربوط به مخزن را نگهداری می‌کند. حذف یا آسیب‌زدن به این پوشه معمولاً به معنای از بین رفتن تاریخچهٔ پروژه است (هرچند فایل‌های کاری ممکن است بدون تغییر باقی بمانند).

**اجزای مهم داخل `.git`**

- **پوشهٔ `objects/`**: پایگاه دادهٔ اصلی اشیاء Git است. Git محتوای فایل‌ها (Blobs)، ساختار دایرکتوری‌ها (Trees)، اطلاعات کامیت‌ها (Commits) و تگ‌های Annotated را به صورت اشیاء ذخیره می‌کند. هر شیء با مقدار هش (معمولاً SHA-1 یا در برخی پیکربندی‌ها SHA-256) نام‌گذاری و فشرده می‌شود.
- **پوشهٔ `refs/`**: شامل ارجاعات (References) به کامیت‌ها است.
  - `heads/`: فایل‌هایی که به نوک شاخه‌های محلی اشاره می‌کنند (Local branches).
  - `tags/`: اشاره‌گرهای مربوط به تگ‌ها.
  - `remotes/`: ارجاع به وضعیت شاخه‌ها در مخازن راه دور (مثلاً `origin/main`).
- **فایل `HEAD`**: یک ارجاع سمبولیک است که نشان می‌دهد در حال حاضر روی کدام شاخه یا کامیت قرار دارید (معمولاً شبیه `ref: refs/heads/main`).
- **فایل `config`**: پیکربندی مخصوص این مخزن را نگهداری می‌کند (آدرس مخازن راه دور، نام کاربری/ایمیل محلی، تنظیمات merge/rebase و غیره).
- **فایل `index`**: نمایندهٔ Staging Area است؛ یک ساختار دودویی که فهرست فایل‌هایی را که برای کامیت بعدی آماده شده‌اند به همراه متادیتا نگه می‌دارد.
- **پوشهٔ `logs/`**: شامل reflog است که تغییرات ارجاعات (مثلاً حرکات `HEAD`) را ثبت می‌کند و برای بازیابی کامیت‌های گمشده بسیار مفید است.
- **پوشهٔ `hooks/`**: اسکریپت‌هایی که در نقاط مختلف چرخهٔ گیت (مثل `pre-commit`, `pre-push`) اجرا می‌شوند؛ نمونه‌ها به همراه پسوند `.sample` قرار دارند.
- **پوشهٔ `info/`**: فایل‌هایی مانند `exclude` را نگه می‌دارد که شبیه `.gitignore` عمل می‌کنند اما به‌صورت محلی و بدون ثبت در تاریخچه هستند.

**نکته دربارهٔ هش اشیاء:** به طور تاریخی Git از SHA-1 برای نام‌گذاری اشیاء استفاده کرده است؛ اما پیاده‌سازی‌های جدید و برخی پیکربندی‌ها می‌توانند از SHA-256 نیز استفاده کنند. این جزئیات پیاده‌سازی در نسخهٔ Git و تنظیمات مخزن نقش دارد.

### نحوهٔ ایجاد پوشهٔ `.git`

برای تبدیل یک دایرکتوری عادی به یک مخزن محلی Git از دستور زیر استفاده کنید:

```bash
git init
```

خروجی نمونه:

```text
Initialized empty Git repository in /path/to/your/project/.git/
```

اجرای `git init` ساختار اولیهٔ پوشهٔ `.git` را ایجاد می‌کند (نظیر `objects/`, `refs/`, `HEAD`, `config` و غیره) و از آن پس دایرکتوری تحت کنترل نسخهٔ Git قرار می‌گیرد.

همچنین هنگام استفاده از `git clone` برای گرفتن یک مخزن از راه دور، پوشهٔ `.git` همراه با تمام تاریخچهٔ پروژه به‌صورت خودکار روی سیستم شما ساخته می‌شود:

```bash
git clone https://github.com/SE-LAB-14043/AZ1-repo.git
```

در پایان، چند نکتهٔ عملی:

- پوشهٔ `.git` را به هیچ‌وجه در داخل تاریخچهٔ مخزن قرار ندهید (نباید آن را commit کنید). معمولاً این پوشه به‌صورت مخفی و محلی نگهداری می‌شود.
- برای گرفتن نسخهٔ پشتیبان از تاریخچهٔ کامل کافی است کل دایرکتوری پروژه (شامل `.git`) را کپی کنید یا از امکانات remote (مثل `git push`) استفاده کنید.
- اگر به دنبال بازگردانی کامیت یا بررسی حرکت‌های اخیر هستید، `git reflog` می‌تواند بسیار مفید باشد (اطلاعات داخل `logs/`).

## منظور از Atomic بودن در Atomic Commit و Atomic Pull Request چیست؟

### Atomic Commit

در Git، منظور از **Atomic Commit** این است که هر Commit یک **واحد منطقی و مستقل از تغییرات** باشد؛ یعنی تمام تغییرات موجود در آن Commit در راستای یک هدف مشخص انجام شده باشند.

به عبارت دیگر، یک Commit نباید چند تغییر نامرتبط را با یکدیگر ترکیب کند.

برای مثال، این Commit مناسب است:

```text
Add navigation bar
```

اگر تغییرات آن فقط مربوط به اضافه‌کردن Navigation Bar باشد، حتی اگر چند فایل HTML، CSS و JavaScript تغییر کرده باشند، Commit همچنان Atomic محسوب می‌شود.

اما Commitی مانند:

```text
Add navigation bar + fix login bug + update README
```

Atomic نیست؛ زیرا چند تغییر مستقل و نامرتبط در یک Commit قرار گرفته‌اند.

### مزایای Atomic Commit

Atomic بودن Commit باعث می‌شود:

- تاریخچه Git خواناتر و قابل فهم‌تر باشد.
- Code Review ساده‌تر انجام شود.
- پیدا کردن منشأ Bug و استفاده از `git bisect` آسان‌تر شود.
- امکان `revert` کردن یک تغییر مشخص بدون تأثیرگذاری روی تغییرات نامرتبط وجود داشته باشد.
- فرآیند Merge و مدیریت تغییرات ساده‌تر شود.

نکته مهم این است که **Atomic به معنی کوچک‌ترین تغییر ممکن نیست**؛ بلکه به معنی **یکپارچگی منطقی تغییرات** است. بنابراین یک Commit می‌تواند چند فایل را تغییر دهد، به شرطی که همه تغییرات برای یک هدف مشخص باشند.

---

### Atomic Pull Request

**Atomic Pull Request** نیز همین مفهوم را در سطح Pull Request دنبال می‌کند. یک Pull Request باید یک **Feature، Bug Fix یا هدف مشخص و منسجم** را دنبال کند و تغییرات نامرتبط با آن را شامل نشود.

برای مثال:

```text
PR: Add Home Page

Commits:
- Add home page structure
- Add home page styles
- Add home page interactions
```

این Pull Request Atomic است، زیرا تمام Commitهای آن مربوط به یک Feature مشخص هستند.

در مقابل، Pull Requestی که همزمان شامل:

```text
- Add Home Page
- Fix Login Bug
- Change Footer
- Update README
```

باشد، Atomic نیست؛ زیرا چند موضوع مستقل را در یک Pull Request ترکیب کرده است.

### تفاوت Atomic Commit و Atomic Pull Request

| مورد | Atomic Commit | Atomic Pull Request |
|---|---|---|
| سطح | یک Commit | یک Pull Request |
| هدف | یک تغییر منطقی | یک Feature یا Bug Fix مشخص |
| تعداد Commit | یک Commit | می‌تواند چند Commit داشته باشد |
| مزیت اصلی | تاریخچه خواناتر و Revert ساده‌تر | Review و Merge ساده‌تر |

بنابراین می‌توان خلاصه کرد:

> **Atomic Commit یعنی هر Commit یک تغییر منطقی و مستقل را نشان دهد؛ Atomic Pull Request یعنی هر Pull Request یک Feature، Bug Fix یا هدف مشخص و منسجم را برای ادغام ارائه کند.**

## تفاوت `fetch`، `pull`، `merge`، `rebase` و `cherry-pick` در Git

در Git این پنج دستور همگی برای مدیریت و انتقال تغییرات بین شاخه‌ها و مخازن استفاده می‌شوند، اما نقش آن‌ها متفاوت است. تفاوت اصلی این است که بعضی از آن‌ها فقط اطلاعات Remote را دریافت می‌کنند، بعضی تغییرات را ادغام می‌کنند و بعضی نیز تاریخچه Commitها را بازنویسی یا Commitهای خاصی را منتقل می‌کنند.

### 1. `git fetch`

دستور `fetch` اطلاعات و Commitهای جدید موجود در **Remote Repository** را دریافت می‌کند، اما تغییراتی در Branch فعلی یا فایل‌های Working Directory ایجاد نمی‌کند.

```bash
git fetch origin
```

برای مثال، اگر در Remote شاخه `main` تغییر کرده باشد، با `fetch` اطلاعات آن دریافت شده و معمولاً در `origin/main` قابل مشاهده خواهد بود، اما `main` محلی شما همچنان بدون تغییر باقی می‌ماند.

بنابراین:

> `fetch` فقط اطلاعات Remote را می‌گیرد و آن‌ها را در Repository محلی به‌روزرسانی می‌کند؛ خودش هیچ ادغامی انجام نمی‌دهد.

---

### 2. `git pull`

دستور `pull` برای دریافت تغییرات از Remote و ادغام آن‌ها در Branch فعلی استفاده می‌شود.

به صورت مفهومی:

```bash
git pull
```

تقریباً معادل انجام این دو عملیات است:

```bash
git fetch
git merge
```

البته `pull` می‌تواند با گزینه‌هایی مانند `--rebase` به جای Merge، از Rebase نیز استفاده کند.

بنابراین تفاوت اصلی:

```text
fetch → فقط دریافت تغییرات
pull  → دریافت تغییرات + ادغام آن‌ها
```

مثلاً اگر هم‌تیمی شما تغییرات جدیدی روی `main` قرار داده باشد، می‌توان با `git pull` آن تغییرات را دریافت و با Branch فعلی یکپارچه کرد.

---

### 3. `git merge`

دستور `merge` برای **ادغام تاریخچه دو Branch** استفاده می‌شود.

برای مثال، فرض کنید روی Branch زیر هستیم:

```bash
git switch main
```

و می‌خواهیم تغییرات Branch `feature/home-page` را وارد `main` کنیم:

```bash
git merge feature/home-page
```

Git تلاش می‌کند تاریخچه دو Branch را با یکدیگر ترکیب کند.

اگر دو Branch تغییرات متعارضی در یک قسمت از فایل داشته باشند، ممکن است **Merge Conflict** ایجاد شود که باید به صورت دستی برطرف شود.

در حالت معمول، Merge تاریخچه قبلی Branchها را حفظ می‌کند و در صورت نیاز یک **Merge Commit** ایجاد می‌کند.

بنابراین:

> `merge` تغییرات یک Branch را با Branch دیگر ادغام می‌کند و ساختار اصلی تاریخچه Branchها را حفظ می‌کند.

---

### 4. `git rebase`

دستور `rebase` نیز برای قرار دادن تغییرات یک Branch روی پایه‌ای جدید استفاده می‌شود، اما برخلاف Merge، تاریخچه Commitها را **بازنویسی** می‌کند.

برای مثال:

```bash
git switch feature
git rebase main
```

در این حالت Commitهای Branch `feature` از نو روی آخرین Commit موجود در `main` اعمال می‌شوند.

قبل از Rebase:

```text
A---B---C  main
  \
   D---E  feature
```

بعد از Rebase:

```text
A---B---C---D'---E'  feature
```

دقت کنید که `D'` و `E'` همان Commitهای قبلی نیستند؛ Commitهای جدیدی با شناسه‌های جدید ایجاد شده‌اند.

مزیت اصلی Rebase این است که می‌تواند تاریخچه‌ای خطی و مرتب ایجاد کند و از ایجاد Merge Commitهای غیرضروری جلوگیری کند.

اما چون Rebase تاریخچه را بازنویسی می‌کند، نباید بدون دقت روی Branchهایی که توسط افراد دیگر استفاده می‌شوند انجام شود.

---

### 5. `git cherry-pick`

دستور `cherry-pick` برای انتقال **یک یا چند Commit مشخص** از یک Branch به Branch دیگر استفاده می‌شود.

برای مثال:

```bash
git switch main
git cherry-pick abc123
```

در این حالت فقط Commit با شناسه `abc123` روی Branch فعلی اعمال می‌شود، نه تمام تغییرات Branch مبدأ.

فرض کنیم:

```text
A---B---C---D  main

  E---F---G  feature
```

اگر فقط Commit `F` را Cherry-pick کنیم:

```text
A---B---C---D---F'
```

تغییرات Commit `F` در Branch `main` اعمال می‌شوند، اما خود Commit با همان شناسه منتقل نمی‌شود؛ Git یک Commit جدید با شناسه جدید ایجاد می‌کند.

این دستور مخصوصاً زمانی مفید است که فقط یک Bug Fix یا تغییر خاص از یک Branch را نیاز داریم و نمی‌خواهیم کل Branch را Merge یا Rebase کنیم.

---

## تفاوت‌ها در یک نگاه

| دستور | عملیات اصلی | تاریخچه را تغییر می‌دهد؟ | ادغام انجام می‌دهد؟ |
|---|---|---|---|
| `fetch` | دریافت اطلاعات Remote | خیر | خیر |
| `pull` | `fetch` + ادغام | بسته به روش ادغام | بله |
| `merge` | ادغام دو Branch | خیر، تاریخچه موجود را حفظ می‌کند | بله |
| `rebase` | انتقال Commitها روی پایه جدید | **بله** | به روش متفاوتی تغییرات را بازاعمال می‌کند |
| `cherry-pick` | انتقال Commit مشخص | Branch مقصد را با Commit جدید تغییر می‌دهد | فقط Commit انتخاب‌شده |

### خلاصه مفهومی

```text
fetch
↓
تغییرات Remote را فقط دریافت کن

pull
↓
تغییرات Remote را دریافت و با Branch فعلی ادغام کن

merge
↓
دو تاریخچه را با حفظ ساختار آن‌ها ادغام کن

rebase
↓
Commitهای یک Branch را روی پایه جدید بازاعمال کن و تاریخچه را خطی‌تر کن

cherry-pick
↓
فقط Commit مشخصی را از یک Branch روی Branch دیگر اعمال کن
```

**نکته کلیدی:** تفاوت `merge` و `rebase` در نحوه برخورد با تاریخچه است؛ `merge` تاریخچه Branchها را حفظ کرده و معمولاً یک نقطه ادغام ایجاد می‌کند، در حالی که `rebase` Commitها را روی پایه جدید بازاعمال کرده و تاریخچه را بازنویسی می‌کند. `cherry-pick` نیز به جای ادغام یک Branch، فقط Commitهای انتخاب‌شده را منتقل می‌کند.



## تفاوت دستورهای reset و revert و restore و switch و checkout را بیان کنید.

## تفاوت دستورهای `reset`، `revert`، `restore`، `switch` و `checkout`

این پنج دستور برای مدیریت وضعیت فایل‌ها، Commitها و Branchها در Git استفاده می‌شوند، اما کاربرد آن‌ها متفاوت است. مهم‌ترین تفاوت این است که `reset` می‌تواند تاریخچه‌ی محلی را جابه‌جا یا بازنویسی کند، `revert` برای ایجاد Commit جدید جهت خنثی‌کردن تغییرات استفاده می‌شود، `restore` برای برگرداندن فایل‌ها و تغییرات آن‌هاست و `switch` و `checkout` بیشتر برای جابه‌جایی بین Branchها استفاده می‌شوند.

### `git reset`

دستور `reset` برای جابه‌جا کردن `HEAD` و در صورت استفاده از گزینه‌های مختلف، تغییر وضعیت `Staging Area` و `Working Directory` استفاده می‌شود.

برای مثال:

```bash
git reset HEAD~1
````

در این حالت آخرین Commit از Branch فعلی حذف نمی‌شود از نظر فایل‌ها، اما `HEAD` به Commit قبلی منتقل شده و تغییرات Commit قبلی به صورت تغییرات Stage نشده در Working Directory باقی می‌مانند.

سه حالت اصلی `reset` عبارت‌اند از:

```bash
git reset --soft HEAD~1
git reset --mixed HEAD~1
git reset --hard HEAD~1
```

#### `--soft`

فقط `HEAD` را جابه‌جا می‌کند و تغییرات Commit قبلی را در Stage نگه می‌دارد.

```bash
git reset --soft HEAD~1
```

#### `--mixed`

حالت پیش‌فرض `reset` است. `HEAD` و Stage را تغییر می‌دهد، اما تغییرات فایل‌ها را در Working Directory نگه می‌دارد.

```bash
git reset --mixed HEAD~1
```

#### `--hard`

`HEAD`، Stage و Working Directory را به وضعیت Commit مقصد برمی‌گرداند و تغییرات موجود ممکن است از بین بروند.

```bash
git reset --hard HEAD~1
```

بنابراین:

> `reset` بیشتر برای اصلاح یا جابه‌جایی تاریخچه‌ی محلی استفاده می‌شود و استفاده از آن روی Commitهایی که قبلاً به Remote Push شده‌اند می‌تواند باعث ایجاد مشکل برای سایر اعضای تیم شود.

---

### `git revert`

دستور `revert` برای خنثی‌کردن تغییرات یک Commit استفاده می‌شود، بدون اینکه Commit قبلی از تاریخچه حذف شود.

برای مثال:

```bash
git revert abc123
```

Git یک Commit جدید ایجاد می‌کند که تغییرات Commit `abc123` را معکوس می‌کند.

به صورت مفهومی:

```text
A---B---C---D
        ↓
      revert C
        ↓
A---B---C---D---R
```

در اینجا Commit `C` همچنان در تاریخچه وجود دارد و Commit جدید `R` اثرات آن را خنثی می‌کند.

این ویژگی باعث می‌شود `revert` برای Branchهای مشترک و Commitهایی که قبلاً روی Remote قرار گرفته‌اند، گزینه‌ی امن‌تری نسبت به `reset` باشد.

بنابراین:

> `reset` تاریخچه را جابه‌جا می‌کند، اما `revert` با ایجاد یک Commit جدید، اثرات یک Commit قبلی را خنثی می‌کند.

---

### `git restore`

دستور `restore` برای بازگرداندن فایل‌ها به یک وضعیت مشخص و مدیریت تغییرات Working Directory و Staging Area استفاده می‌شود.

برای مثال، اگر تغییراتی در یک فایل ایجاد کرده باشیم و بخواهیم آن‌ها را حذف کنیم:

```bash
git restore index.html
```

این دستور فایل را به وضعیت ثبت‌شده در Commit فعلی برمی‌گرداند.

همچنین می‌توان با استفاده از `--staged` یک فایل را از Stage خارج کرد:

```bash
git restore --staged index.html
```

در این حالت فایل از Staging Area خارج می‌شود، اما تغییرات آن در Working Directory باقی می‌مانند.

بنابراین:

> `restore` برای مدیریت و بازگرداندن تغییرات فایل‌ها استفاده می‌شود و برخلاف `reset` برای تغییر تاریخچه‌ی Commitها طراحی نشده است.

---

### `git switch`

دستور `switch` برای جابه‌جایی بین Branchها استفاده می‌شود و در نسخه‌های جدید Git به عنوان دستور تخصصی‌تر برای مدیریت Branchها معرفی شده است.

برای جابه‌جایی به یک Branch موجود:

```bash
git switch main
```

برای ایجاد یک Branch جدید و جابه‌جایی به آن:

```bash
git switch -c feature/home-page
```

در این حالت Branch جدید ایجاد شده و `HEAD` نیز روی آن قرار می‌گیرد.

بنابراین:

> `switch` به‌طور مشخص برای جابه‌جایی و ایجاد Branchها طراحی شده است.

---

### `git checkout`

دستور `checkout` یک دستور قدیمی‌تر و چندمنظوره در Git است که می‌تواند برای جابه‌جایی بین Branchها و همچنین بازگرداندن فایل‌ها استفاده شود.

برای جابه‌جایی به Branch:

```bash
git checkout main
```

برای ایجاد Branch جدید و جابه‌جایی به آن:

```bash
git checkout -b feature/home-page
```

همچنین `checkout` می‌تواند برای بازگرداندن یک فایل استفاده شود:

```bash
git checkout -- index.html
```

به دلیل اینکه `checkout` چند کاربرد مختلف دارد، Git دستورات `switch` و `restore` را معرفی کرده است تا این وظایف از یکدیگر جدا و واضح‌تر شوند.

بنابراین:

> `checkout` یک دستور قدیمی و چندمنظوره است، در حالی که `switch` برای Branchها و `restore` برای فایل‌ها کاربرد مشخص‌تری دارند.

---

## تفاوت کلی دستورات

| دستور      | کاربرد اصلی                                      | تاریخچه Commit را تغییر می‌دهد؟ | کاربرد روی Branch مشترک |
| ---------- | ------------------------------------------------ | ------------------------------- | ----------------------- |
| `reset`    | جابه‌جایی `HEAD` و تغییر Stage/Working Directory | بله، در برخی حالت‌ها            | با احتیاط               |
| `revert`   | خنثی‌کردن یک Commit                              | خیر                             | مناسب و ایمن‌تر         |
| `restore`  | بازگرداندن فایل‌ها و مدیریت Stage                | خیر                             | مناسب                   |
| `switch`   | جابه‌جایی یا ایجاد Branch                        | خیر                             | مناسب                   |
| `checkout` | جابه‌جایی Branch یا بازگرداندن فایل              | بسته به نحوه استفاده            | قدیمی‌تر و چندمنظوره    |

### تفاوت مفهومی `reset` و `revert`

یکی از مهم‌ترین تفاوت‌های این سؤال، تفاوت `reset` و `revert` است.

فرض کنیم تاریخچه به شکل زیر باشد:

```text
A---B---C---D
```

اگر Commit `C` را با `reset` حذف کنیم، تاریخچه می‌تواند به شکل زیر تغییر کند:

```text
A---B
```

در حالی که با `revert`:

```text
A---B---C---D---R
```

Commit `C` همچنان در تاریخچه وجود دارد، اما Commit جدید `R` اثرات آن را خنثی می‌کند.

به همین دلیل، برای Commitهایی که قبلاً Push شده‌اند، معمولاً `revert` نسبت به `reset` انتخاب مناسب‌تری است.

---

### تفاوت `switch` و `checkout`

`switch` و `checkout` هر دو می‌توانند برای جابه‌جایی بین Branchها استفاده شوند:

```bash
git switch main
```

و:

```bash
git checkout main
```

اما `switch` دستور جدیدتر و تخصصی‌تری برای مدیریت Branchها است. در مقابل، `checkout` علاوه بر Branch، کاربردهای دیگری مانند بازگرداندن فایل‌ها و رفتن به یک Commit مشخص را نیز دارد.

به همین دلیل، در Git مدرن معمولاً استفاده از:

```bash
git switch
```

برای مدیریت Branchها و:

```bash
git restore
```

برای مدیریت فایل‌ها، خواناتر و واضح‌تر از استفاده‌ی چندمنظوره از `checkout` است.

### جمع‌بندی

به‌صورت خلاصه:

* `reset` برای جابه‌جایی `HEAD` و در برخی حالت‌ها تغییر Stage و Working Directory استفاده می‌شود و می‌تواند تاریخچه‌ی محلی را تغییر دهد.
* `revert` اثرات یک Commit را با ایجاد یک Commit جدید خنثی می‌کند و تاریخچه‌ی قبلی را حفظ می‌کند.
* `restore` برای بازگرداندن تغییرات فایل‌ها و مدیریت وضعیت Staging Area استفاده می‌شود.
* `switch` برای ایجاد و جابه‌جایی بین Branchها استفاده می‌شود.
* `checkout` دستور قدیمی و چندمنظوره‌ای است که هم برای Branchها و هم برای فایل‌ها و Commitها استفاده می‌شده است.

در نتیجه، می‌توان این پنج دستور را به صورت زیر به خاطر سپرد:

```text
reset
↓
جابجایی HEAD و تغییر وضعیت تاریخچه/Stage

revert
↓
خنثی‌کردن یک Commit با ایجاد Commit جدید

restore
↓
بازگرداندن تغییرات فایل‌ها

switch
↓
جابه‌جایی بین Branchها

checkout
↓
دستور قدیمی و چندمنظوره برای Branch، Commit و فایل
```




## منظور از stage یا همان index چیست؟ دستور stash چه کاری را انجام می‌دهد؟

### Stage یا Staging Area

در Git، **Stage** یا **Staging Area** یک ناحیه‌ی میانی بین فایل‌های پروژه و Commit است که برای مشخص‌کردن تغییراتی استفاده می‌شود که قرار است در **Commit بعدی** ثبت شوند.

به عبارت دیگر، وقتی یک یا چند فایل را تغییر می‌دهیم، این تغییرات بلافاصله وارد Commit نمی‌شوند؛ ابتدا باید آنها را با استفاده از دستور `git add` وارد Stage کنیم.

به‌صورت مفهومی، فرآیند به شکل زیر است:

```text
Working Tree
     ↓
   git add
     ↓
Staging Area
     ↓
  git commit
     ↓
Repository
```

بنابراین Stage به Git می‌گوید:

> «از میان تغییراتی که در پروژه انجام داده‌ام، این بخش‌ها آماده‌اند و می‌خواهم در Commit بعدی ثبت شوند.»

---

### Index چیست؟

در Git، واژه‌ی **Index** در واقع نام فنی ساختاری است که وضعیت Stage را نگهداری می‌کند.

این اطلاعات معمولاً در فایل زیر قرار دارد:

```text
.git/index
```

به همین دلیل در مستندات Git ممکن است به جای عبارت **Staging Area** از عبارت **Index** نیز استفاده شود.

بنابراین در کاربرد معمول Git:

```text
Stage ≈ Staging Area ≈ Index
```

هر سه اصطلاح به همان مفهوم آماده‌سازی تغییرات برای Commit اشاره دارند، اگرچه از نظر فنی Index ساختار داخلی Git است که وضعیت فایل‌های Stage شده را نگهداری می‌کند.

---

### مثال از Stage

فرض کنیم در یک پروژه سه فایل زیر را تغییر داده‌ایم:

```text
index.html
style.css
script.js
```

اگر دستور زیر را اجرا کنیم:

```bash
git status
```

ممکن است Git وضعیت را به شکل زیر نشان دهد:

```text
Changes not staged for commit:
    modified: index.html
    modified: style.css
    modified: script.js
```

یعنی هر سه فایل تغییر کرده‌اند، اما هنوز هیچ‌کدام برای Commit بعدی انتخاب نشده‌اند.

حالا فرض کنیم فقط تغییرات `index.html` و `style.css` آماده هستند:

```bash
git add index.html style.css
```

در این حالت وضعیت به صورت مفهومی چنین خواهد بود:

```text
Stage:
- index.html
- style.css

Working Tree:
- script.js
```

اگر اکنون Commit کنیم:

```bash
git commit -m "update homepage"
```

فقط تغییرات `index.html` و `style.css` وارد Commit می‌شوند و تغییرات `script.js` همچنان در Working Tree باقی می‌ماند.

---

### چرا Stage اهمیت دارد؟

یکی از مهم‌ترین کاربردهای Stage این است که به توسعه‌دهنده اجازه می‌دهد **محتوای Commit را به صورت دقیق انتخاب کند**.

فرض کنیم همزمان دو کار انجام داده‌ایم:

```text
- اضافه‌کردن Navigation Bar
- برطرف‌کردن Login Bug
```

ممکن است تغییرات هر دو کار در فایل‌های مختلف پروژه وجود داشته باشند.

به جای اینکه همه تغییرات را با:

```bash
git add .
```

وارد یک Commit کنیم، می‌توانیم تغییرات مربوط به هر موضوع را جداگانه Stage کرده و Commit کنیم.

برای مثال:

```bash
git add navbar.html navbar.css
git commit -m "add navigation bar"
```

و سپس:

```bash
git add login.js
git commit -m "fix login validation"
```

در نتیجه تاریخچه‌ی Git به جای یک Commit بزرگ و نامرتبط، دو Commit مشخص و معنادار خواهد داشت.

این موضوع ارتباط مستقیمی با مفهوم **Atomic Commit** دارد؛ زیرا Stage امکان انتخاب دقیق تغییرات و ایجاد Commitهای مستقل و منطقی را فراهم می‌کند.

---

### خارج‌کردن تغییرات از Stage

اگر فایلی را با دستور زیر Stage کرده باشیم:

```bash
git add style.css
```

اما بعد تصمیم بگیریم که فعلاً نمی‌خواهیم آن فایل در Commit بعدی قرار بگیرد، می‌توانیم آن را از Stage خارج کنیم:

```bash
git restore --staged style.css
```

این دستور **تغییرات فایل را حذف نمی‌کند**؛ فقط آن را از Staging Area خارج می‌کند.

بنابراین:

```text
قبل:

Working Tree
     ↓
   Stage
style.css


بعد:

Working Tree
style.css

Stage
خالی
```

---

## دستور `stash` چیست؟

دستور **`git stash`** برای ذخیره‌ی موقت تغییرات Commit نشده استفاده می‌شود.

گاهی اوقات در حال کار روی یک Feature هستیم و تغییرات ما هنوز کامل نشده‌اند و بنابراین نمی‌خواهیم برای آنها Commit ایجاد کنیم. در همین زمان ممکن است مجبور شویم موقتاً روی Branch دیگری کار کنیم.

در چنین شرایطی می‌توانیم تغییرات فعلی را با:

```bash
git stash
```

موقتاً کنار بگذاریم.

Git تغییرات را در یک Stash ذخیره می‌کند و Working Tree را به وضعیت تمیزتری برمی‌گرداند.

نکته مهم این است که:

> `git stash` تغییرات را حذف نمی‌کند؛ بلکه آنها را به صورت موقت ذخیره می‌کند تا بعداً بتوان آنها را بازیابی کرد.

---

### مشاهده Stashها

برای مشاهده‌ی Stashهای موجود می‌توان از دستور زیر استفاده کرد:

```bash
git stash list
```

برای مثال:

```text
stash@{0}: WIP on feature/home-page
stash@{1}: WIP on feature/navbar
stash@{2}: WIP on stage
```

هر کدام از این موارد یک مجموعه تغییرات ذخیره‌شده را نشان می‌دهد.

---

### تفاوت `git stash pop` و `git stash apply`

برای بازیابی تغییرات Stash شده دو دستور مهم وجود دارد:

```bash
git stash apply
```

و:

```bash
git stash pop
```

دستور:

```bash
git stash apply
```

تغییرات Stash را دوباره روی Working Tree اعمال می‌کند، اما خود Stash را نگه می‌دارد.

در مقابل:

```bash
git stash pop
```

تغییرات را بازیابی می‌کند و در صورت موفقیت، Stash مربوطه را از لیست حذف می‌کند.

بنابراین می‌توان به صورت خلاصه گفت:

```text
git stash apply
    ↓
اعمال تغییرات + نگه‌داشتن Stash


git stash pop
    ↓
اعمال تغییرات + حذف Stash
```

---

### تفاوت Stage و Stash

| مورد             | Stage / Index                                 | Stash                                   |
| ---------------- | --------------------------------------------- | --------------------------------------- |
| هدف              | آماده‌سازی تغییرات برای Commit                | ذخیره موقت تغییرات                      |
| دستور اصلی       | `git add`                                     | `git stash`                             |
| ارتباط با Commit | مستقیماً برای Commit بعدی استفاده می‌شود      | لزوماً قرار نیست Commit شود             |
| دائمی است؟       | تا زمانی که Commit یا Unstage شود             | موقتی است                               |
| کاربرد اصلی      | انتخاب دقیق محتوای Commit                     | کنار گذاشتن موقت کار                    |
| بازیابی          | با `git restore --staged` می‌توان Unstage کرد | با `git stash apply/pop` بازیابی می‌شود |

---

### جمع‌بندی

به طور خلاصه، **Stage یا Index** ناحیه‌ای است که تغییرات انتخاب‌شده برای Commit بعدی در آن قرار می‌گیرند. با استفاده از `git add` می‌توان تغییرات را وارد Stage کرد و سپس با `git commit` آنها را به عنوان بخشی از تاریخچه‌ی Git ثبت کرد.

وجود Stage باعث می‌شود توسعه‌دهنده بتواند تغییرات مختلف را از یکدیگر تفکیک کرده و Commitهای **Atomic و معنادار** ایجاد کند؛ بنابراین حتی اگر چند فایل تغییر کرده باشند، می‌توان فقط تغییرات مرتبط با یک هدف مشخص را در یک Commit قرار داد.

در مقابل، **`git stash`** برای زمانی استفاده می‌شود که تغییرات هنوز آماده‌ی Commit نیستند، اما لازم است موقتاً آنها را کنار بگذاریم؛ برای مثال زمانی که باید از یک Branch به Branch دیگری برویم و نمی‌خواهیم تغییرات ناقص خود را Commit کنیم.

بنابراین می‌توان مفهوم این دو را به شکل زیر خلاصه کرد:

> **Stage یعنی انتخاب تغییراتی که قرار است در Commit بعدی ثبت شوند؛ Stash یعنی ذخیره‌ی موقت تغییراتی که فعلاً نمی‌خواهیم Commit کنیم.**




## مفهوم Snapshot به چه معناست؟ ارتباط آن با Commit چیست؟

### Snapshot چیست؟

در Git، منظور از **Snapshot** یا «تصویر لحظه‌ای»، نمایشی از **وضعیت فایل‌ها و ساختار پروژه در یک لحظه مشخص از تاریخچه پروژه** است.

به عبارت دیگر، هر Snapshot مشخص می‌کند که در یک نقطه مشخص از تاریخچه Git، فایل‌های پروژه چه محتوایی داشته‌اند و ساختار آن‌ها چگونه بوده است.

برای مثال فرض کنیم پروژه در ابتدا به شکل زیر باشد:

```text
project/
├── index.html
├── style.css
└── script.js
```

در یک لحظه مشخص، وضعیت پروژه می‌تواند به صورت زیر باشد:

```text
index.html  → Version A
style.css   → Version A
script.js   → Version A
```

این وضعیت یک **Snapshot** از پروژه است.

اگر بعداً `index.html` و `style.css` را تغییر دهیم، وضعیت جدید پروژه مثلاً چنین خواهد شد:

```text
index.html  → Version B
style.css   → Version B
script.js   → Version A
```

این وضعیت نیز یک Snapshot جدید محسوب می‌شود.

نکته مهم این است که Snapshot بیان‌کننده‌ی **وضعیت پروژه در یک زمان مشخص** است، نه صرفاً توضیح تغییراتی که از وضعیت قبلی انجام شده‌اند.

---

### ارتباط Snapshot با Commit


 وقتی دستور زیر را اجرا می‌کنیم:

```bash
git commit -m "add home page"
```

Git یک Commit جدید ایجاد می‌کند که وضعیت پروژه را در آن لحظه ثبت می‌کند.

هر Commit علاوه بر اطلاعاتی مانند:

```text
Author
Committer
Date
Commit Message
Parent Commit
```

به یک **Root Tree** نیز اشاره می‌کند که وضعیت فایل‌ها و پوشه‌های پروژه در آن Commit را مشخص می‌کند. 

بنابراین می‌توان رابطه را به صورت زیر نشان داد:

```text
Commit
   │
   └──► Snapshot
          │
          ├── index.html
          ├── style.css
          └── script.js
```

به همین دلیل گفته می‌شود:

> **Commit در Git یک Snapshot است، نه یک Diff.**

این نکته در درک نحوه کار Git بسیار مهم است.

---

### Commit در Git Diff نیست

یک تصور اشتباه رایج این است که Commit را به شکل زیر در نظر بگیریم:

```text
Commit 1:
+ اضافه شدن index.html

Commit 2:
+ اضافه شدن style.css
- حذف یک خط از index.html
```

یعنی تصور کنیم هر Commit فقط مجموعه‌ای از تغییرات نسبت به Commit قبلی است.

اما Git به این شکل Commit را ذخیره نمی‌کند.

در مدل Git، هر Commit به Snapshot مربوط به وضعیت پروژه در آن لحظه اشاره می‌کند.

برای مثال:

```text
Commit A
   │
   └── Snapshot A
       ├── index.html
       ├── style.css
       └── script.js


Commit B
   │
   └── Snapshot B
       ├── index.html
       ├── style.css
       └── script.js
```

Snapshot مربوط به Commit B وضعیت کامل مورد انتظار پروژه در آن Commit را مشخص می‌کند.

---

### پس Git چگونه Diff را نمایش می‌دهد؟

اگر Commitها Snapshot باشند، ممکن است این سؤال ایجاد شود که Git چگونه می‌فهمد بین دو Commit چه تغییراتی اتفاق افتاده است؟

پاسخ این است که **Diff به صورت پویا از مقایسه‌ی Snapshotها محاسبه می‌شود**.

برای مثال فرض کنیم:

```text
Commit A
   ↓
Snapshot A

index.html = Version A
style.css  = Version A
script.js  = Version A
```

و:

```text
Commit B
   ↓
Snapshot B

index.html = Version B
style.css  = Version A
script.js  = Version A
```

وقتی Git بخواهد تفاوت Commit B با Commit A را نمایش دهد، Snapshotهای آنها را با یکدیگر مقایسه می‌کند و نتیجه را به صورت Diff نمایش می‌دهد:

```text
Snapshot A
     │
     │ compare
     ▼
Snapshot B
     │
     ▼
Diff
index.html changed
```

بنابراین **Diff چیزی نیست که به عنوان هسته اصلی Commit در آن ذخیره شده باشد**؛ بلکه Git می‌تواند با مقایسه‌ی Snapshot دو Commit، Diff میان آنها را محاسبه کند.  

---

### Snapshot چگونه در ساختار داخلی Git ذخیره می‌شود؟

برای درک دقیق‌تر مفهوم Snapshot باید با سه نوع Object مهم در Git آشنا شویم:

```text
Blob
Tree
Commit
```

#### Blob

**Blob** محتوای فایل را نگهداری می‌کند.

برای مثال:

```text
index.html
     ↓
   Blob
     ↓
محتوای index.html
```

Blob به تنهایی نام فایل را نگهداری نمی‌کند؛ بلکه محتوای فایل را نشان می‌دهد.  

---

#### Tree

**Tree** ساختار دایرکتوری‌ها و ارتباط نام فایل‌ها با Objectهای مربوطه را مشخص می‌کند.

به صورت ساده:

```text
Tree
├── index.html → Blob
├── style.css  → Blob
└── script.js  → Blob
```

بنابراین Tree می‌تواند ساختار یک Directory را توصیف کند و به Blobها و Treeهای دیگر اشاره داشته باشد.  

---

#### Commit

Commit به Root Tree مربوط به Snapshot پروژه اشاره می‌کند و همچنین اطلاعاتی مانند Parent، Author، Committer و Commit Message را نگهداری می‌کند.  

در نتیجه می‌توان ساختار را به صورت زیر نمایش داد:

```text
Commit
   │
   ├── Parent Commit
   │
   ├── Author
   ├── Committer
   ├── Commit Message
   │
   └── Root Tree
          │
          ├── index.html → Blob
          ├── style.css  → Blob
          └── src/       → Tree
```

به همین دلیل Snapshot در Git از طریق همین ساختار Objectها قابل نمایش است.

---

### Git الزاماً همه فایل‌ها را در هر Snapshot دوباره کپی نمی‌کند

یکی از نکات مهم درباره Snapshot این است که منظور از Snapshot این نیست که Git در هر Commit یک کپی کامل و مستقل از تمام فایل‌های پروژه ایجاد می‌کند.

Git Objectها را بر اساس محتوای آنها شناسایی می‌کند و Objectهای مشابه می‌توانند توسط Snapshotهای مختلف مورد استفاده قرار بگیرند.

برای مثال اگر `script.js` بین دو Commit هیچ تغییری نکرده باشد:

```text
Commit A
   ↓
Tree A
   └── script.js → Blob X


Commit B
   ↓
Tree B
   └── script.js → Blob X
```

هر دو Snapshot می‌توانند به همان Blob مربوط به `script.js` اشاره کنند.

بنابراین Snapshot از نظر مفهومی وضعیت کامل پروژه را نشان می‌دهد، اما Git برای جلوگیری از ذخیره‌سازی غیرضروری داده‌های تکراری از Objectهای مشترک استفاده می‌کند.  

---

### Snapshot و مفهوم Hash

Git Objectها را با **Object ID** یا همان Hash شناسایی می‌کند.

این موضوع باعث می‌شود تغییر در محتوای یک Object باعث ایجاد Object متفاوتی شود.

برای مثال:

```text
index.html
     │
     ▼
Content A
     │
     ▼
Hash A
```

اگر محتوای فایل تغییر کند:

```text
index.html
     │
     ▼
Content B
     │
     ▼
Hash B
```

در نتیجه Snapshot جدید نیز می‌تواند به Objectهای متفاوتی اشاره کند.

این ساختار یکی از دلایل مهمی است که Git می‌تواند تغییرات تاریخچه و ارتباط بین Objectها را به شکل قابل اعتماد مدیریت کند.  

---


### Snapshot در مقایسه با Diff

تفاوت این دو مفهوم را می‌توان به شکل زیر خلاصه کرد:

| مورد                | Snapshot                        | Diff                                         |
| ------------------- | ------------------------------- | -------------------------------------------- |
| مفهوم               | وضعیت پروژه در یک لحظه مشخص     | تفاوت بین دو وضعیت                           |
| ارتباط با Commit    | Commit به Snapshot اشاره می‌کند | از مقایسه Snapshotها به دست می‌آید           |
| بیانگر              | وضعیت فایل‌ها و ساختار پروژه    | تغییرات بین دو وضعیت                         |
| مثال                | وضعیت کامل پروژه در Commit B    | چه خطوطی بین A و B تغییر کرده‌اند            |
| نحوه استفاده در Git | بخش اصلی مدل Objectهای Git      | معمولاً به صورت محاسبه‌شده نمایش داده می‌شود |

### جمع‌بندی

در Git، **Snapshot به معنای وضعیت پروژه در یک نقطه مشخص از زمان است**. هر Commit یک Snapshot از وضعیت پروژه در زمان ایجاد آن Commit را ثبت می‌کند و از طریق Root Tree به ساختار فایل‌ها و Objectهای مربوط به آنها اشاره می‌کند.

نکته بسیار مهم این است که **Commit در Git یک Diff نیست، بلکه یک Snapshot است**. Git برای نمایش تغییرات بین دو Commit، Snapshot مربوط به آنها را با یکدیگر مقایسه کرده و Diff را به صورت پویا محاسبه می‌کند.  

بنابراین می‌توان مفهوم را به صورت زیر خلاصه کرد:

> **Snapshot یعنی وضعیت پروژه در یک لحظه مشخص؛ Commit در Git به عنوان ثبت آن Snapshot در تاریخچه عمل می‌کند و Diff نیز از مقایسه Snapshotهای مختلف به دست می‌آید.**

## تفاوت‌های local repository و remote repository </pre>

### Local Repository

در Git، منظور از **Local Repository** نسخه‌ای از Repository است که روی **سیستم شخصی توسعه‌دهنده** قرار دارد و توسعه‌دهنده می‌تواند به صورت مستقیم روی آن کار کند.

Local Repository شامل تاریخچه Git، Commitها، Branchها و Objectهای مربوط به پروژه است و اطلاعات اصلی آن در پوشه‌ی `.git` نگهداری می‌شود.

برای مثال، اگر پروژه‌ای روی سیستم ما در مسیر زیر قرار داشته باشد:

```text
project/
├── index.html
├── style.css
├── script.js
└── .git/
```

پوشه‌ی `.git` بخش اصلی Local Repository را تشکیل می‌دهد.

توسعه‌دهنده می‌تواند بدون نیاز به اتصال دائمی به اینترنت، بسیاری از عملیات Git مانند موارد زیر را انجام دهد:

```bash
git add
git commit
git branch
git switch
git merge
git rebase
git log
git diff
```

برای مثال، وقتی دستور زیر را اجرا می‌کنیم:

```bash
git commit -m "add home page"
```

یک Commit ابتدا در **Local Repository** ایجاد می‌شود و هنوز لزوماً در Remote Repository قرار نگرفته است.

---

### Remote Repository

**Remote Repository** نسخه‌ای از Repository است که معمولاً روی یک سرور یا سرویس میزبانی Git قرار دارد و برای **اشتراک‌گذاری و همکاری بین توسعه‌دهندگان** استفاده می‌شود.

یکی از رایج‌ترین سرویس‌ها برای میزبانی Remote Repository، [GitHub](https://github.com/?utm_source=chatgpt.com) است.

برای مثال، اگر پروژه‌ای روی GitHub قرار داشته باشد، Repository موجود در GitHub یک Remote Repository برای توسعه‌دهندگان پروژه محسوب می‌شود.

Remote Repository به اعضای تیم اجازه می‌دهد تغییرات خود را با یکدیگر به اشتراک بگذارند و Branchها و Commitهای مختلف را روی یک مخزن مشترک مدیریت کنند.

---

### ارتباط Local Repository و Remote Repository

Local و Remote دو Repository مستقل هستند که می‌توانند از طریق Git با یکدیگر ارتباط داشته باشند.

به صورت مفهومی:

```text
Local Repository
      │
      │ git push
      ▼
Remote Repository
      │
      │ git fetch / git pull
      ▼
Local Repository
```

برای مثال، فرض کنیم یک Commit جدید در Local Repository ایجاد کرده‌ایم:

```bash
git add .
git commit -m "add home page"
```

در این مرحله Commit فقط در Local Repository وجود دارد.

برای ارسال آن به Remote Repository می‌توانیم از:

```bash
git push origin main
```

استفاده کنیم.

در نتیجه Commit به Remote Repository منتقل می‌شود.

---

### Local Repository می‌تواند چند Remote داشته باشد

یک Local Repository الزاماً فقط یک Remote ندارد.

برای مثال می‌توان Remoteهای مختلفی داشت:

```text
origin
upstream
```

برای مشاهده آنها:

```bash
git remote -v
```

مثلاً:

```text
origin    https://github.com/user/project.git
upstream  https://github.com/company/project.git
```

این قابلیت در پروژه‌های مختلف، به‌خصوص هنگام کار با Forkها، کاربرد زیادی دارد.

---

### تفاوت در محل ذخیره‌سازی

یکی از تفاوت‌های اصلی این دو Repository، محل قرارگیری آنهاست.

**Local Repository:**

```text
سیستم شخصی توسعه‌دهنده
        ↓
.git
```

**Remote Repository:**

```text
سرور / سرویس Git
        ↓
GitHub / GitLab / Bitbucket / ...
```

بنابراین Local Repository معمولاً برای توسعه و ثبت محلی تغییرات استفاده می‌شود، در حالی که Remote Repository برای اشتراک‌گذاری و همکاری تیمی مورد استفاده قرار می‌گیرد.

---

### تفاوت در دسترسی به اینترنت

یکی از مزایای مهم Git این است که بسیاری از عملیات اصلی در Local Repository بدون نیاز به اینترنت قابل انجام هستند.

برای مثال می‌توانیم بدون اتصال به Remote:

```bash
git add .
git commit -m "update homepage"
git log
git branch
git merge
```

را انجام دهیم.

اما برای تبادل اطلاعات با Remote Repository معمولاً به ارتباط با اینترنت نیاز داریم؛ برای مثال:

```bash
git push
git fetch
git pull
```

---

### تفاوت Local و Remote Repository در یک نگاه

| مورد            | Local Repository                 | Remote Repository                        |
| --------------- | -------------------------------- | ---------------------------------------- |
| محل قرارگیری    | سیستم توسعه‌دهنده                | سرور یا سرویس میزبانی Git                |
| هدف اصلی        | توسعه و مدیریت محلی پروژه        | اشتراک‌گذاری و همکاری                    |
| دسترسی          | معمولاً مستقیم و محلی            | از طریق شبکه                             |
| Commit          | می‌تواند بدون اینترنت ایجاد شود  | Commitهای Push شده در آن قابل مشاهده‌اند |
| Branch          | Branchهای محلی را نگهداری می‌کند | Branchهای Remote را نگهداری می‌کند       |

### جمع‌بندی

**Local Repository** مخزنی است که روی سیستم توسعه‌دهنده قرار دارد و محل اصلی انجام تغییرات، ایجاد Commit، ساخت Branch و انجام بسیاری از عملیات Git است.

**Remote Repository** مخزنی است که روی یک سرور یا سرویس میزبانی Git قرار دارد و برای اشتراک‌گذاری کد، همکاری اعضای تیم، نگهداری نسخه مشترک پروژه و هماهنگ‌سازی تغییرات استفاده می‌شود.

ارتباط این دو از طریق دستورهایی مانند `push`، `fetch` و `pull` انجام می‌شود.

بنابراین می‌توان به صورت خلاصه گفت:

> **Local Repository محیط محلی توسعه‌دهنده برای کار و ثبت تغییرات است، در حالی که Remote Repository نسخه‌ی مشترک پروژه در یک سرور است که برای اشتراک‌گذاری، همکاری تیمی و تبادل تغییرات میان توسعه‌دهندگان استفاده می‌شود.**
